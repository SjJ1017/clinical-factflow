# 数据集可行性与研究适配性

核查日期：2026-09-09。以下区分官方公开事实、许可条款和对本项目的研究判断。尚未申请任何受限数据、代表用户签署协议或向作者发送消息；未下载任何完整研究数据集。

## 决策

**主任务候选优先看 MIMIC-CDM 与 ClinicalBench；需要立即公开复现的路线，优先审计 MedCaseReasoning 中检查证据齐全的病例。非医疗扩展优先试 FinQA 的跨证据、多步推理子集。** 没有一个候选同时无条件满足“多专业证据齐全、完备事实真值、天然专家知识差异、自由改编公开”四项要求。

这里的“优先”指值得进入下一步数据审计，不代表已经证明当前模型上有足够难度。所有候选都必须分别检查：病例／任务级答案、关键证据标注、推理依据是否可用，以及它们是不是完整真值。专业词汇多、数据量大或最终标签准确，均不能替代这些检查。

| 候选 | 证据与专业分工 | 可用监督 | 主要阻碍 | 本项目定位 |
|---|---|---|---|---|
| **MIMIC-CDM** | 病史、体检、真实检验、影像分表；分工依据很强 | 诊断、实际治疗／操作、诊断路径参照 | 受限访问与云端处理；仅四类腹部疾病 | **医疗主候选**，适合研究信息获取与整合，不能声称标签多样性高 |
| **ClinicalBench / ClinicalLab** | 多科室、检验／影像／病理报告 | 多项医生标注任务及诊断依据 | 禁训练、限制修改／衍生和公开；需书面澄清本项目操作 | **有条件主候选**；无法确认授权时不宜把项目锁在它上面 |
| **MedCaseReasoning** | 复杂病例叙述中可含检查数值、影像、病理，病例间不齐全 | 最终诊断与来自病例文章的诊断理由 | LLM 整理、理由不完备、需人工无损分区和源许可审计 | **开放路线首选审计对象**，不是未经筛选直接全量使用 |
| **MedCase-Structured** | FHIR 资源方便按检查类型分配 | 诊断与源病例对应 | LLM 转换误差；排除影像依赖病例 | 结构化表示对照；不替代真实多模态诊断主集 |
| **FinQA** | 财务报表表格、叙述和附注 | 专家答案、支持事实、可执行推理程序 | 很多题偏局部计算；“不同专家”不是原生实验变量 | **非医疗第一候选**，需跨来源证据子集 |
| **ContractNLI** | 合同定义、义务、例外、终止条款 | 三分类判断＋证据跨度 | 专业领域较窄，跨专家差异弱 | 限定条件／例外遗漏的解释性对照 |
| **DiscoveryBench** | 领域数据、变量说明、领域知识、统计分析工作流 | 假设与分面评估；部分可重算 | 不是完备事实真值；需要代码工具与更复杂评测 | 长期跨专业方向，当前骨架的直接使用成本高 |
| **DDxPlus** | 结构化症状和既往史，缺少丰富真实检验／影像分工 | 合成疾病标签、鉴别诊断概率 | 与用户要求的多专业检查协作不够贴合 | 仅机制对照，不作主集 |
| **diagnosis-text** | 第一人称症状描述 | 十类疾病标签 | 检查证据和过程监督弱，且再次生成改写 | 不推荐作主集 |

## ClinicalBench：能申请，但许可不适合直接假定“可自由加工”

这里核查的是 **WeixiangYAN/ClinicalLab 中的 ClinicalBench**，不是另一个同名临床预测 benchmark。官方提供中英文示例、数据许可和[申请表](https://forms.gle/Tkq5UTinW7bBB6388)。本次只读请求成功取得该表的公开内容，包含逐节同意条款，未填写或提交。README 写的是申请后邮件发送、48 小时；这是作者公布的安排，并非本次验证过的实际响应时间。[官方仓库](https://github.com/WeixiangYAN/ClinicalLab)

官方数据卡列出 1,500 例、24 科室、150 疾病，包含病例摘要、检查报告和医生标注的诊断／诊断依据等多任务字段。它有现实专业分工所需的内容，但**没有给出每一个任意生成命题的完备真假标注**。所谓 data-leakage-free 是作者对构建过程的主张，不能当作所有后续模型均未见过数据的保证。[官方数据卡](https://github.com/WeixiangYAN/ClinicalLab/blob/main/data_examples/DATASET_CARD.md)

本次已下载并逐页读取官方英文许可 PDF。关键条款如下：[数据许可 §§2–5](https://github.com/WeixiangYAN/ClinicalLab/blob/main/DATA_LICENSE.pdf)

| 条款 | 直接含义 | 对本项目的影响 |
|---|---|---|
| §2 | 非商业学术评测；禁止用数据训练模型；禁止修改或衍生 | 不能自行假定“只是训练一个 fact-profile 错误预测器”不受限制 |
| §3 | 仅许可使用者使用，防止未经授权访问或泄漏 | 下载权限不自动覆盖外部 API 或所有合作者 |
| §4 | 可分析模型／agent 及其推理结果；不可发表修改版、衍生作品或实际病例内容 | 聚合研究结果可分享；含病例事实的公开 trace viewer 不可默认发布 |
| §5 | 禁止再分发，包括部分／衍生；项目须链接和署名 | 发布代码与汇总指标，与发布病例／原子事实是两件事 |

**研究判断：获取文件可行，按当前许可直接执行整个研究方案存在实质不确定性。** §2 的禁止修改与 §4 的允许分析如何覆盖临时证据分区、原子化侧车和特征提取，文本并不够明确。临时把原始字段分给三个评测 agent，与重新发行一个分区数据集不同；不宜把二者一概说成已允许或已违法。许可未明确点名云 API，但第三方使用／再分发限制使 OpenCode→模型供应商的处理链必须先确认。该结论是对条款适用范围的判断，不是作者已作出的授权答复。

建议申请时同时确认 [permission-request.md](permission-request.md) 中的具体操作。特别要覆盖**输出特征训练失败预测器、模型提供商处理、向 mentor 展示病例／原子事实**，而不仅仅写“academic research”。如果作者仅允许本地原始评测与聚合指标，就把它作为验证集，主研究换到可加工的来源。

原项目已有一个容易遗漏的问题：影像 `impression` 在 imaging-diagnosis 任务中就是答案，却曾随 findings 进入输入。新适配器默认不喂 impression，影像任务开启 impression 会报错；但病例摘要仍须逐例检查诊断泄漏和检查信息重复。原始公开 JSON 若存在无效转义，新代码明确报错，避免未经记录修复来源文件。

## MIMIC-CDM：临床协作结构最贴合，但四类标签和处理环境是代价

[官方 v1.1](https://physionet.org/content/mimic-iv-ext-cdm/1.1/) 是 MIMIC-IV 的预处理派生集：2,400 名真实患者，阑尾炎、胆囊炎、憩室炎、胰腺炎四类腹部疾病。病史、体检、检验、微生物和影像按字段／文件组织；保留诊断和治疗操作参照，原任务允许按需请求检查。只取每项检验的首次记录，不能用于声称完整病情动态。

**为何比症状分类更合适：** A 读病史／体检，B 读影像报告，C 读检验／微生物，这些是记录本身的来源分区；任务可以检查某个实验室值是否传到决策者、是否被错误解释、是否改变疾病严重度与处理建议。分信息有工作流依据，但仍是我们设计的多 agent 改编，原数据没有标注三个医生真实如何沟通。

**为什么仍可能不够：** 只有四类主诊断，纯分类可能很快饱和。若诊断全对但治疗、必要检查和条件推断不同，不能把“四分类准确率”当作唯一结果变量。实际治疗不等于所有情况下唯一正确或最优治疗；应使用作者任务定义和医生审查过的指标，不能把任意额外建议标错。只研究 rich fact profile→四类诊断错误，需要先确认有足够错误样本。

访问需 PhysioNet credentialing、CITI 培训和该数据集 DUA；可以取得已加工的 CDM 文件，不必为本项目从完整 MIMIC 自行重建。学生／博士后准入需导师参考信息，审批时间以实际平台为准。[官方准入说明](https://mimic.mit.edu/docs/faq/how-to-get-access.html)

它的 GitHub 代码许可证不替代医疗数据 DUA。PhysioNet 目前强烈推荐本地 LLM；云服务需核实零留存、不训练、无人审阅等要求，不能确认处理细节就不要使用。**现有 OpenCode Go／minimax 默认链没有在本次调查中得到相应合规证明**，因此这条路线应按本地生成＋本地抽取规划，或由机构确认的处理环境。[PhysioNet 官方 LLM 政策](https://physionet.org/news/post/llm-responsible-use/)

团队成员需要各自准入，病例原文／图片不能默认放在公开论文或网页中。这会限制可公开交付的 viewer 和错误案例展示，但不阻止公开方法代码与允许的聚合研究结果。[官方 FAQ](https://physionet.org/about/faqs/)

## MedCaseReasoning：开放病例路线，但要保留来源审计

官方 HF 提供 `case_prompt`、`final_diagnosis`、`diagnostic_reasoning`、PMCID 和文章信息，卡片标注 MIT。公开样例可见数值检验、影像和组织病理内容，因此“文本形式”并不等于“仅症状、不专业”；关键是文本是否记录专业检查及其语境。[官方数据集](https://huggingface.co/datasets/zou-lab/MedCaseReasoning)

14,489 例来自公开病例文章；研究用 o4-mini 组织病例问答与理由、另一个模型过滤，医生审查了随机 100 例，而非逐条人工穷尽标注整个数据集。作者承认理由不完备、部分病例存在信息不足或泄漏答案的问题。[论文方法与限制](https://arxiv.org/html/2505.11733v1)

**适配方案：** 先审计检查齐全病例，用原始 `case_prompt` 做无损、连续跨度分区；按病史／体检、影像、检验／病理分配，每个分区保留原文位置。不能让 LLM 为缺失科室补写报告，否则错误归因会混入数据生成器。保留全部未分区文字，不按 gold 理由筛掉干扰信息；只用理由来评测，不用于构造“恰好能解题”的分区。

病例是否有三个实质互补分区、其决定性信息是否在摘要里，尚未全量测量，不能先承诺筛后样本量。比较 train/test 时按原始病例／PMCID 划分；同病例的不同任务／拓扑不能跨训练测试泄漏。公开文章也可能已经进入模型预训练。

**许可可行性：** 释放文件的 MIT 标识便于使用，但不代表每篇被转载文章都被重新授予 MIT。PMC 明确要求逐文章查看许可证，OA 子集内也有不同条款；系统取回原文章需使用 PMC 允许的接口。计划公开包含原文或重构报告的研究产物时，应保留 PMCID→源许可清单，优先选择允许改编和再分发的记录。[PMC 官方复用规则](https://pmc.ncbi.nlm.nih.gov/tools/openftlist/)

**结论：** 最值得立即做数据适配审计的开放临床候选。先用公开许可清楚、检查证据互补的部分；不要把整理出的理由当成完备原子事实真值。

## MedCase-Structured：分配容易，真实性要单独验证

该项目把 MedCaseReasoning 转成 FHIR，包含 Observation、DiagnosticReport、Condition 等资源，答案独立存储，卡片标注 MIT。它明确说明为 LLM 生成、可能有抽取／编码错误，并排除影像依赖病例。卡片目录说明为 1,732 个病例，而 HF 自动 viewer 行数为 2,254；一个病例包含多个文件，不能把 viewer 行数当患者数。[官方卡片及目录说明](https://huggingface.co/datasets/system-technologies/MedCase-Structured)

**研究判断：** 适合控制“结构化编码→自然语言交接”是否丢失条件，资源类型也便于分区。但 Observation 多不表示多个专业证据都在，同一原句拆成很多 FHIR resource 也不增加真实信息。影像依赖病例被排除，会削弱影像专家角色研究。使用前须核对源句、数值单位、诊断隐藏及上游许可，不作为 ClinicalBench 的直接等价替代。

## FinQA：非医疗中监督最干净的近期候选

FinQA 有专家标注的财务问题、答案、支持事实和多步计算程序，输入包含表格与叙述。官方项目网站给出数据 CC BY 4.0，并指向数据／代码下载。不要套用某个第三方镜像对许可证的说法。[官方项目](https://finqasite.github.io/)、[作者仓库](https://github.com/czyssrs/FinQA)

**协作 rationale：** 可以把表格核算、会计口径／附注、最终财务解释作为工作分工。原始财务报告的数值、期间、单位、口径是具体未知证据，不是预训练知识能可靠补出的值。可执行程序使“证据没到”“值到了但期间／单位变了”“操作数选错”“计算错”有可复查的区别。

**限制：** 原 benchmark 没有天然多专家对话；不少题只是从一张表取数做简单运算，把一行分给一人属于人为制造通信瓶颈。仅选择经输入结构审计、确实跨表格和文本／多步计算的题作为目标子群，并同时报告整个可用集的覆盖比例。不要只选某模型做错的题再当总体效果。角色应基于会计工作分工，不能假设通用 LLM 不懂乘除。

**可行性：** 文件直接公开，标签和程序易核对，成本低于真实 EHR；但规模较老，当前模型难度未知。先做小规模难度与专业性审计，再决定是否主跑。完整财报引用／重新分发的范围需随来源核查，CC BY 的署名与修改说明要保留。

## ContractNLI：适合条件／例外流失，但跨专业性弱

607 份 NDA、17 个固定假设，标签为蕴含／矛盾／未提及，并标证据跨度；法律例外与否定是关键难点。官方许可 CC BY 4.0，提供 JSON。[官方数据和条款](https://stanfordnlp.github.io/contract-nli/)

**协作 rationale：** 按定义条款、义务与例外、终止／存续条款分工，观察交接是否丢失限定条件；证据 span 可用于检查“哪些条款真的足以支撑判断”。这比仅有最终类标更适合验证 fact profile。

**限制与结论：** 一份 NDA 通常不需要互不相通的多个专业；这里更像分段合同审阅，不宜包装成现实跨学科团队。17 假设固定，角色容易对特定问题过拟合。适合作为解释性方法的第二领域对照，优先级低于证据类型真正互补的主任务。其 gold 的 Contradiction 不能由当前双向蕴含 matcher 的两个 NO 自动得到，任务 evaluator 与 fact matcher 必须分开。

## DiscoveryBench：最接近领域专家＋统计专家，但超出当前轻量任务形态

原始论文报告 264 个真实任务、六个领域，要求结合数据、元数据和目标进行统计及领域推理；另有合成任务。元数据包括领域知识、变量语义和工作流提示。[原始论文](https://arxiv.org/html/2407.01725v1)、[作者元数据说明](https://github.com/allenai/discoverybench/blob/main/discoverybench/README.md)

**协作 rationale：** 一位解释测量含义／领域假设，一位负责统计建模，一位审查结论适用范围。原始表格可能很大，“所有信息全塞进提示词”本身有真实成本；专业工具和数据访问可成为分工依据。

**限制：** 需要代码执行、数据查询和可复算的中间结果；只有自然语言交流的当前 runner 不能声称复现原任务。Gold hypothesis 不是所有正确发现的全集，语义 evaluator 也不是无误真值。对于“事实清楚且监督可靠”的当前目标，它比 FinQA 更难建立可信测量，因此保留为后续研究方向。

仓库使用 ODC-By，许可文字明确区分数据库权利和其中各项内容的权利；实际来源数据要逐项检查，不能从根目录许可证推导所有源表都可任意再分发。[官方许可证](https://github.com/allenai/discoverybench/blob/main/LICENSE)

## DDxPlus 与 diagnosis-text：明确降级，不因易获取而提升优先级

DDxPlus 官方英语版为 CC BY 4.0，包含合成症状／既往史、类别／多选取值、诊断及鉴别概率。它适合检验精确观察值的分配与保留，但没有本项目期望的丰富真实检验、影像和科室报告结构。[官方英语发布页](https://figshare.com/articles/dataset/DDXPlus_Dataset_English_/22687585)、[字段说明](https://github.com/mila-iqia/ddxplus)

你提供的 diagnosis-text **正是 DDxPlus 的进一步简化派生**：选十类疾病，只留下年龄、性别、症状，再让 GPT-3.5 转为第一人称文字，保留 `sentence1` 和 `label`。卡片的具体许可信息也未完整填写。[该数据集卡片](https://huggingface.co/datasets/ninaa510/diagnosis-text)

因此，不把它当作“低成本替代 ClinicalBench”。它适合症状分类；即使加入三个“专家”提示，也不能补出本来不存在的检查证据和过程监督。DDxPlus 适合离线机制 sanity check，diagnosis-text 连结构化原始值都进一步丢失，均不作为主研究首选。

## 进入实验前的实际判据

对主候选抽取一个由来源／任务类别分层的审计集，逐例记录：独立证据分区、数值与否定条件、诊断／答案泄漏、gold 支持范围、关键结论是否需要跨分区结合、许可是否允许拟执行的加工和展示。这里不预设尚未测量的“有多少例合格”。

只有通过审计后才冻结 cohort 与分配文件、校验其哈希，再运行预先固定的 topology × role × information 实验。**角色名造成不同输出，可以研究 role prompting；要声称专家知识壁垒，需另有能力测量或真实差异化模型／工具证据。** 具体对照与可解释性边界见 [研究设计](research-design.md)。
